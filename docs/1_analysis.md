# РОЗДІЛ 1. АНАЛІЗ АНАЛОГІВ ТА ТЕХНІЧНЕ ЗАВДАННЯ

## 1.2 Аналіз існуючих аналогів

### 1.2.1 Методика відбору та критерії аналізу

Для інженерного порівняння відібрано три програмні системи, кожна з яких покриває одну зі складових розроблюваного рішення:

- **Starbucks (Mobile Order & Pay, Starbucks Rewards)** — передзамовлення та програма лояльності в мережі кав'ярень;
- **Toast** — хмарна платформа для закладів харчування: POS, онлайн-замовлення, резервації та управління залом;
- **OpenTable** — глобальна платформа онлайн-бронювання столиків із пошуком доступності в реальному часі.

Аналіз виконано виключно за системними параметрами: архітектурний патерн, протоколи взаємодії, стек даних, механізми узгодженості та відмовостійкості, обмеження масштабування. Параметри інтерфейсу, вартості та ринкової популярності не розглядалися.

Примітка щодо джерел. Розробники аналізованих систем не публікують повних архітектурних специфікацій. Технічні відомості отримано з публічних описів інженерних вакансій, інженерних профілів та відкритих публікацій (див. перелік джерел наприкінці підрозділу). Відомості, які не підтверджено публічно, позначено як «не розкрито» і не використовуються як підстава для висновків. Розділ «Архітектурні обмеження» містить інженерну оцінку наслідків задокументованих рішень, а не повідомлення про інциденти.

### 1.2.2 Starbucks (Mobile Order & Pay, Starbucks Rewards)

**Архітектурний патерн.** Відкриті дані вказують на мікросервісну архітектуру з подієвою обробкою на базі Apache Kafka; зафіксовано міграцію застарілого моноліту на Scala до мікросервісів на Java (Spring Boot). Мікросервісний підхід забезпечує незалежне масштабування сервісів замовлень і лояльності, проте міграція з моноліту свідчить про наявність успадкованого технічного боргу.

**Протоколи взаємодії.** Асинхронний обмін подіями — Apache Kafka. Транспорт клієнтського API публічно не специфіковано; для мобільного застосунку типовим є REST поверх HTTPS (не підтверджено).

**Стек даних.** Специфікація не розкрита. У публічних матеріалах згадуються MySQL, експериментальна передача даних із Kafka до Cassandra та Azure Event Hub (на рівні proof of concept). Production-використання цих компонентів не підтверджено.

**Архітектурні обмеження:**
- відсутність у публічно задокументованій архітектурі ресурсного шару для бронювання конкретного місця: система оперує замовленням, а не просторовим ресурсом;
- оцінка часу підготовки замовлення визначається завантаженістю закладу, що вимагає актуальних даних про чергу в реальному часі;
- залежність від міграції успадкованих компонентів ускладнює еволюцію домену лояльності.

### 1.2.3 Toast

**Архітектурний патерн.** Мікросервісна архітектура: серверні сервіси реалізовано мовами Java та Kotlin (Dropwizard), контейнеризовано, розгорнуто в AWS. Взаємодія між сервісами подієва, за публічними описами — на основі Apache Pulsar; у вимогах до вакансій також згадуються Kafka та RabbitMQ. Клієнтська частина POS — Android-застосунок (Java, Kotlin).

**Протоколи взаємодії.** REST та gRPC між контейнеризованими сервісами; GraphQL в окремих доменах; асинхронні події через Pulsar/Kafka; двостороння синхронізація з POS-терміналами.

**Стек даних.** Amazon DynamoDB (NoSQL), Amazon Aurora (PostgreSQL), Amazon RDS, Amazon S3; з AWS-сервісів також ECS та Lambda. Мовна та СУБД-поліглотність підвищує гнучкість, але ускладнює забезпечення транзакційної цілісності між сховищами.

**Архітектурні обмеження:**
- гетерогенний набір брокерів повідомлень (Pulsar, Kafka, RabbitMQ згадуються у публічних описах) збільшує операційну складність;
- двостороння синхронізація з POS вимагає розв'язання конфліктів між локальним та хмарним станом;
- розподіл даних між DynamoDB та Aurora ускладнює гарантії узгодженості без розподілених транзакцій.

### 1.2.4 OpenTable

**Архітектурний патерн.** Мікросервісна подієво-орієнтована архітектура (Event-Driven Architecture) на Apache Kafka, розгортання на базі Kubernetes. Окремий сервіс availability search обчислює доступність столиків і обслуговує пошук із низькою затримкою.

**Протоколи взаємодії.** RESTful API; Apache Kafka для розповсюдження змін інвентарю, конфігурації та політик до систем доступності.

**Стек даних.** C#/.NET, Redis, in-memory та розподілені кеші. Основну СУБД не розкрито. Висока швидкодія пошуку досягається кешуванням похідних даних доступності.

**Архітектурні обмеження:**
- розповсюдження змін через Kafka у кеші доступності забезпечує eventual consistency; відображена доступність може не збігатися з актуальним станом на момент підтвердження;
- коректність фіксації броні потребує окремої авторитетної перевірки поза кешем; механізм публічно не розкрито;
- обслуговування кешів та подієвого конвеєра в глобальному масштабі підвищує вартість інфраструктури.

### 1.2.6 Аналітичний висновок

Аналіз показав, що всі розглянуті системи побудовані як розподілені мікросервісні платформи з подієвою взаємодією через брокери повідомлень (Apache Kafka, Apache Pulsar). Такий підхід забезпечує горизонтальне масштабування та слабку зв'язаність сервісів, однак має два інженерні наслідки. По-перше, асинхронне розповсюдження змін у кеші та похідні сховища (OpenTable) забезпечує eventual consistency, що допустимо для пошуку, але недостатньо в момент фіксації броні конкретного ресурсу. По-друге, гетерогенність брокерів і сховищ (Toast) підвищує операційну складність та ускладнює гарантії узгодженості. Публічно задокументовані архітектури не розкривають механізму атомарної фіксації ресурсу за конкурентного доступу, а Starbucks не оперує просторовим ресурсом взагалі.

Для розроблюваної системи обрано двоступеневий захист: розподілене блокування в Redis (`SET NX PX`) із тимчасовим утриманням місця (TTL) відсікає конкурентні запити на рівні застосунку, а exclusion constraint у PostgreSQL гарантує цілісність часових інтервалів навіть у разі відмови блокування. Платіжні операції захищено Idempotency Key, доставку подій персоналу забезпечено WebSocket із Redis Pub/Sub без опитування сервера, автозвільнення броні виконується фоновими задачами Celery Beat. Джерелом істини є PostgreSQL, що усуває залежність коректності від стану кешу. Відмовостійкість забезпечується тим, що відмова Redis-блокування не порушує цілісність даних (останню лінію захисту утримує PostgreSQL), а повторні запити платежів не призводять до подвійного списання.

Обраний підхід має компроміс. Використання Redis та Celery замість Kafka або Pulsar зменшує операційну складність і є достатнім для навантажень регіональної мережі, але Redis Pub/Sub не гарантує доставки та не зберігає журнал подій; цей недолік компенсується відновленням стану з PostgreSQL під час повторного підключення клієнта. Використання Python (FastAPI) поступається JVM-стекам за пропускною здатністю одного інстансу, що компенсується асинхронною моделлю та горизонтальним масштабуванням stateless-сервісів. Подієва абстракція дозволяє за потреби замінити Redis Pub/Sub на Kafka без зміни доменної логіки. Проєктування відповідних компонентів, схеми БД та State Machine викладено в Розділі 2.

## 1.5. Постановка задачі та формування вимог (модель To-Be, Core Features, NFRs)

### 1.5.1. Концептуальна модель To-Be

Передбачено заміну ручних і опитувальних механізмів єдиним серверним контуром, у якому клієнтський застосунок, екран бариста та панель менеджера працюють з одним джерелом достовірних даних (PostgreSQL). Взаємодія реалізується через API на FastAPI; координація конкурентного доступу, розсилання подій і черга фонових задач забезпечуються компонентами Redis та Celery.

Процес 1 (To-Be): 1) клієнт формує кошик і виконує оплату; 2) API реєструє замовлення із ключем ідемпотентності, статус платежу підтверджується webhook-повідомленням шлюзу; 3) замовлення ставиться в чергу, розраховується орієнтовний час готовності; 4) подія розсилається через Redis Pub/Sub на екран бариста по WebSocket; 5) зміна статусу бариста транслюється клієнту в реальному часі; 6) під час готовності клієнт отримує push-сповіщення.

Процес 2 (To-Be): 1) клієнт обирає місце на інтерактивній карті залу й інтервал часу; 2) API отримує блокування Redis для пари «місце — інтервал»; 3) транзакція створює бронь, а обмеження EXCLUDE у PostgreSQL відхиляє будь-який перетин інтервалів; 4) клієнт отримує підтвердження або повідомлення про зайняте місце з альтернативами; 5) подія надходить на екран адміністратора; 6) фонова задача звільняє бронь, якщо клієнт не підтвердив прибуття протягом 20–30 хвилин; 7) за наявності замовлення приготування ініціюється до запланованого часу прибуття.

Процес 3 (To-Be): 1) коворкінг-сесія відкривається під час підтвердження прибуття; 2) тарифікація виконується за фактичним часом; 3) перед завершенням сесії система перевіряє наступну бронь місця; 4) за відсутності конфлікту та підтвердженої оплати сесія продовжується автоматично; 5) під час завершення візиту без неявки до журналу додається бонусна операція; 6) правила антифроду перевіряють частоту операцій та частку неявок.

### 1.5.2. Функціональні вимоги (Core Features)

#### Модуль «Замовлення та черга»

- FR-01. Формувати кошик з позицій меню з урахуванням цін і акцій закладу, приймати оплату через платіжний шлюз з ключем ідемпотентності та ставити оплачене замовлення у віртуальну чергу з розрахунком орієнтовного часу готовності.
- FR-02. Транслювати нові замовлення, бронювання та зміни їх статусів клієнтові та на екрани бариста й адміністратора через WebSocket з розсиланням подій між екземплярами API за допомогою Redis Pub/Sub.

#### Модуль «Бронювання»

- FR-03. Відображати інтерактивну карту залу з актуальним станом і атрибутами місць (розетка, тиха зона, місткість) та створювати бронювання без перетину інтервалів за конкурентних запитів (блокування в Redis, обмеження EXCLUDE у PostgreSQL).
- FR-04. Автоматично звільняти бронь, якщо клієнт не підтвердив прибуття протягом 20–30 хвилин, і надсилати йому повідомлення про звільнення.
- FR-05. Пов'язувати бронювання із замовленням, ініціюючи приготування позицій до запланованого часу прибуття.

#### Модуль «Коворкінг»

- FR-06. Тарифікувати коворкінг-сесію за фактичним часом перебування та автоматично продовжувати її за відсутності конфліктуючої броні й за наявності підтвердженої оплати.

#### Модуль «Лояльність»

- FR-07. Нараховувати бонуси за відвідування без неявок через незмінний журнал бонусних операцій і виявляти аномалії нарахування за правилами антифроду.

#### Модуль «Адміністрування та доступ»

- FR-08. Керувати меню, цінами, акціями та конфігурацією залу через панель менеджера з рольовим розмежуванням доступу (клієнт, бариста, адміністратор, менеджер).

### 1.5.4. Постановка задачі

Таким чином, метою кваліфікаційної роботи є проєктування та розробка клієнт-серверної системи з подієво-орієнтованою доставкою оновлень у реальному часі та безконфліктним керуванням конкурентним бронюванням для вирішення задачі коректного обслуговування замовлень і бронювання місць у мережі кав'ярень за вимірюваних обмежень на затримку (p95 не більше 200 мс за 300 RPS), консистентність (0 подвійних бронювань) і відмовостійкість (доступність 99,5 %). Реалізація передбачає Python 3.11+ (FastAPI, Celery), PostgreSQL та Redis як основні компоненти серверної частини.
