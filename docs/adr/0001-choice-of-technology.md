## Context

Бронювання місця виконується за схемою «перевірити відсутність перетину інтервалу, потім записати бронювання». За рівня ізоляції READ COMMITTED (за замовчуванням у PostgreSQL) дві конкурентні транзакції можуть одночасно зчитати стан «місце вільне» та обидві записати бронювання: виникає гонка даних (race condition), що порушує інваріант системи.

Вимоги та обмеження, що визначають рішення:

- SRS-NFR-CONS-01: із 1000 паралельних запитів на одне місце та інтервал успішним повинен бути рівно один.
- SRS-NFR-CONS-02: виконання SRS-NFR-CONS-01 не повинно залежати від доступності Redis.
- SRS-NFR-PERF-02: p95 часу створення бронювання не більше 400 мс за 100 RPS запису.
- Backend API масштабується горизонтально (кілька екземплярів), тому блокування у пам'яті процесу неприйнятне.
- Стек і середовище: PostgreSQL 15, Redis 7 (уже використовується для Pub/Sub, брокера Celery та лічильників лімітів), SQLAlchemy 2.0 async з asyncpg, один вузол Docker Compose, реплікація PostgreSQL не передбачена.
- Пул з'єднань з БД обмежений (десятки з'єднань), тоді як кількість конкурентних запитів може перевищувати його на порядок.

Потрібно обрати механізм, який гарантує коректність незалежно від логіки застосунку та не вичерпує пул з'єднань за конкурентного доступу до одного місця.

## Alternatives

| № | Альтернатива | Забезпечення коректності | Інженерні обмеження |
| :-: | :--- | :--- | :--- |
| A | Песимістичне блокування рядка місця (SELECT ... FOR UPDATE) | Так, серіалізація в межах транзакції | Транзакція утримує блокування та з'єднання з БД до завершення; N конкурентних запитів створюють N очікуючих транзакцій і вичерпують пул; ризик взаємоблокувань за бронювання кількох місць в одній операції |
| B | Оптимістичне блокування (поле версії) | Так, конфлікт виявляється під час запису | За високого попиту на одне місце більшість запитів завершується повтором; кожна успішна бронь змінює версію й серіалізує записи; потрібен цикл повторів у застосунку |
| C | Розподілене блокування Redis без обмеження в БД | Ні, лише за непорушності блокування | Блокування може завершитися за TTL під час паузи процесу або повільної транзакції, а втрата даних Redis при перезапуску знімає блокування; порушує SRS-NFR-CONS-02 |
| D | Лише обмеження EXCLUDE в PostgreSQL | Так, незалежно від застосунку | Конкуруючі INSERT очікують завершення першої транзакції (як для унікального індексу) і потім завершуються помилкою; кожен із N запитів займає з'єднання з БД до вирішення конфлікту; ранньої відмови немає |
| E | Рекомендаційне блокування PostgreSQL (pg_advisory_xact_lock) та перевірка запитом | Так, серіалізація в межах транзакції | Очікуючі сесії також утримують з'єднання з БД, як і в варіанті A; без обмеження в БД коректність залежить від коду запиту |
| F | Блокування Redis та обмеження EXCLUDE (обрано) | Так, остаточну гарантію надає БД | Два механізми потребують окремого тестування; залежність від розширення btree_gist і специфічних можливостей PostgreSQL |

## Decision

Обрано варіант F: двоступеневий захист із блокуванням у Redis та обмеженням цілісності в PostgreSQL.

**Рівень 1, блокування в Redis (SeatLock Port, адаптер Redis Seat Lock).** Ключ `lock:seat:{seat_id}`, команда `SET key token NX PX 5000` із випадковим токеном власника; звільнення виконується Lua-скриптом, що видаляє ключ лише за збігу токена. Запит, який не отримав блокування, повертає код 409 без звернення до БД. Блокування є оптимізацією й не є єдиним захистом: за недоступності Redis сервіс продовжує обробку без блокування.

**Рівень 2, обмеження в PostgreSQL (SQL Booking Repository).**

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE bookings
    ADD CONSTRAINT bookings_no_overlap
    EXCLUDE USING gist (
        seat_id WITH =,
        tstzrange(starts_at, ends_at, '[)') WITH &&
    )
    WHERE (status IN ('created', 'checked_in'));
```

Порушення обмеження (SQLSTATE 23P01, exclusion_violation) перетворюється адаптером на доменну помилку SeatAlreadyBooked і код 409. Часткове обмеження (WHERE) звільняє інтервал після скасування або закінчення терміну бронювання.

**Обґрунтування вибору технічними метриками:**

1. Коректність (SRS-NFR-CONS-01, CONS-02) гарантується атомарністю та ACID-властивостями PostgreSQL незалежно від стану Redis і від логіки застосунку; це відсутнє у варіанті C.
2. Навантаження на БД за конкурентного доступу до одного місця зменшується: через блокування до бази доходить один запит із N, а решта N−1 отримує відмову в Redis без використання з'єднання; у варіантах A, D, E кожен із N запитів займає з'єднання з пулу.
3. TTL блокування 5 с перевищує цільовий p95 часу створення бронювання (400 мс) у 12,5 раза, тому блокування не завершується під час нормальної обробки.
4. Додаткового контейнера не потрібно: Redis уже входить до архітектури (Pub/Sub, брокер Celery, лічильники лімітів).

Припущення про зменшення навантаження на пул з'єднань підлягає експериментальній перевірці в Розділі 3 (див. нижче).

## Consequences

**Позитивні:**

- Відсутність подвійних бронювань гарантується на рівні СУБД і не залежить від коректності коду та доступності Redis.
- Відмова Redis призводить до зниження продуктивності, а не до порушення коректності (деградація до варіанта D).
- Швидка відмова (код 409) для більшості конкурентних запитів без транзакції в БД.
- Метрика частки конфліктів бронювання (SRS-NFR-OBS-01) вимірюється на двох рівнях: відмови блокування та порушення EXCLUDE.
- Додаткова вартість інфраструктури відсутня: використовується наявний контейнер Redis.

**Негативні та ризики:**

- Складність: два механізми потребують окремих тестів, зокрема ін'єкції відмови Redis (зупинка контейнера під час навантаження).
- Налаштування TTL: надто малий TTL допускає завершення блокування під час повільної транзакції (тоді захист переходить до БД); надто великий затримує повторні спроби після збою власника.
- Вузол Redis без реплікації є точкою відмови для швидкої відмови, але не для коректності.
- Залежність від розширення btree_gist: потрібна міграція з виконанням сирого SQL або ExcludeConstraint діалекту PostgreSQL у SQLAlchemy; керовані сервіси PostgreSQL зазвичай дозволяють розширення, але це підлягає перевірці під час розгортання поза демонстраційним середовищем.
- Прив'язка до PostgreSQL (vendor lock-in на рівні можливостей СУБД): обмеження EXCLUDE відсутнє в MySQL та SQLite, перехід на іншу СУБД потребує перепроєктування захисту.
- GiST-індекс збільшує вартість запису та обсяг сховища порівняно зі звичайним B-tree.
- Гранулярність блокування за місцем (не за інтервалом) короткочасно серіалізує бронювання неперетинних інтервалів одного місця; для цільового навантаження це допустимо.

**Верифікація та перегляд рішення:**

- Тести: SRS-FUN-07 і SRS-NFR-CONS-01 (1000 паралельних запитів, рівно 1 успіх), SRS-NFR-CONS-02 (зупинка Redis під час тесту, результат не змінюється).
- Експеримент у Розділі 3: порівняння варіантів A, C, D, F за p95 затримки створення бронювання, піковою кількістю з'єднань з БД та часткою помилок на сценарії 1000 паралельних запитів.
- Критерій перегляду: якщо різниця p95 та піку з'єднань між варіантами D і F не перевищує 10 %, блокування Redis вилучається для спрощення архітектури, а рішення замінюється новим ADR зі статусом Superseded.
