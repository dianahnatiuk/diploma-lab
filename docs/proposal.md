# Thesis Proposal

> Кваліфікаційний проєкт бакалавра
> Спеціальність F2 — Інженерія програмного забезпечення

---

## 1. Робоча назва проєкту

* **UA:** Хмароорієнтована сервісно-орієнтована платформа автоматизованого планування подорожей та управління бронюваннями на основі методів комбінаторної оптимізації
* **EN:** Cloud-Native Service-Oriented Platform for Automated Travel Itinerary Planning and Booking Management Based on Combinatorial Optimization Methods

---

## 2. Актуальність та проблематика

Наявні цифрові сервіси планування подорожей поділяються на два класи, кожен із яких має структурні обмеження:

1. **Клас 1 — генеративні асистенти на основі великих мовних моделей:** Системи коректно інтерпретують природномовний запит користувача, проте не гарантують фізичної реалізовності згенерованого плану: маршрут не верифікується на відповідність реальному часу переміщення між точками, годинам роботи закладів і бюджетним обмеженням як системі взаємопов'язаних умов. Результатом є правдоподібний, але нереалізовний артефакт.
2. **Клас 2 — транзакційні платформи бронювання:** Системи ефективно вирішують задачу пошуку й резервування окремої одиниці розміщення, проте не формують цілісного маршруту та не координують бронювання різнотипних закладів у межах однієї поїздки.

**Інженерна проблематика:** Побудова реалізовного маршруту є задачею маршрутизації з часовими вікнами (*Vehicle Routing Problem with Time Windows — VRPTW*), що належить до класу NP-важких. Формування розкладу бронювань персоналу закладу є задачею розподілу ресурсів з обмеженнями того ж класу складності. Обидві задачі характеризуються часом розв'язання, який неприпустимо утримувати в межах синхронного HTTP-запиту, що зумовлює необхідність асинхронної архітектури з чергами завдань, механізмами відмовостійкості та контуром спостережуваності за станом обчислювальних задач.

## 3. Сформована ідея продукту

**Тип системи за архітектурою:** Хмароорієнтована сервісно-орієнтована вебплатформа з асинхронною подієво-керованою взаємодією компонентів, побудована за принципами **Clean Architecture** з ізоляцією доменного ядра оптимізації від інфраструктурних адаптерів.

### Декомпозиція на сервіси

| Сервіс | Відповідальність | Технологічне ядро |
| :--- | :--- | :--- |
| **api-gateway** | Автентифікація, авторизація (RBAC), маршрутизація запитів, rate limiting | Django REST Framework |
| **optimization-service** | Розв'язання задач комбінаторної оптимізації (VRPTW, розподіл ресурсів) | FastAPI + Google OR-Tools (CP-SAT) |
| **ai-orchestrator** | Інтерпретація природномовного запиту, формування множини кандидатів, генерація векторних представлень | Python, Gemini API |
| **notification-worker** | Асинхронна доставка сповіщень про зміну статусу бронювань | Celery worker |

Взаємодія між `api-gateway` та `optimization-service` реалізується асинхронно через брокер повідомлень Redis із патерном **«завдання — статус — результат»**, що забезпечує незалежне масштабування обчислювального компонента та стійкість системи до пікових навантажень.

**Ключове архітектурне рішення:** Єдина математична модель комбінаторної оптимізації (CP-SAT) застосовується до двох структурно споріднених задач різних предметних областей — побудови маршруту подорожі та формування розкладу бронювань персоналу. Доменне ядро солвера ізольоване від конкретної предметної області через абстракцію моделі обмежень.

## 4. Детальний опис функціоналу (Core Features)

* **F1. Асинхронна генерація оптимізованого маршруту подорожі:** Користувач формує запит у природномовній або структурованій формі. `ai-orchestrator` інтерпретує намір, `optimization-service` розв'язує задачу VRPTW з урахуванням обмежень (години роботи, реальний час переміщення, бюджет, ліміт тривалості). Виконання асинхронне з відстеженням статусу через polling або Server-Sent Events (SSE).
* **F2. Оптимізований розподіл ресурсів при бронюванні послуг:** Запит на бронювання обробляється тим самим обчислювальним ядром з іншою конфігурацією обмежень (графік персоналу, місткість ресурсу, тривалість обслуговування, підтверджені бронювання). Система призначає виконавця і часовий слот, мінімізуючи час очікування.
* **F3. Мультитенантна реєстрація різнотипних закладів та подій:** Узагальнена модель `Venue` з типізацією (готель, заклад харчування, музей тощо) дозволяє реєструвати заклади без дублювання структур. Бронювальні ресурси (`Facility`) та персонал (`Staff`) підключаються опційно. Модель `Event` обслуговує події з часовими вікнами.
* **F4. Рольова модель контролю доступу (RBAC) з ізоляцією даних орендарів:** Три ролі: `traveler`, `business_admin`, `staff`. Ізоляція даних між орендарями гарантує, що власник закладу отримує доступ виключно до сутностей власного закладу на рівні шару доступу до даних (ORM/SQL filters).
* **F5. Персоналізовані рекомендації на основі векторної схожості:** Профіль користувача, подорож і заклад представляються у вигляді векторних вкладень (embeddings), що зберігаються в PostgreSQL із розширенням `pgvector`. Пошук виконується через обчислення косинусної схожості з індексацією HNSW.
* **F6. Механізм верифікованих відгуків із перевіркою права на публікацію:** Публікація відгуку дозволяється виключно за наявності підтвердженого факту завершеного досвіду (завершене бронювання чи відвідана подія). Перевірка виконується як інваріант доменної моделі на серверному шарі.
* **F7. Контур спостережуваності обчислювальних задач (Observability):** Збір метрик виконання задач оптимізації (час розв'язання, кількість обмежень, частка задач без розв'язку). Метрики експортуються в Prometheus і візуалізуються в Grafana, а наскрізне трасування реалізується через OpenTelemetry.

## 5. Обґрунтування технологічного стеку

| Категорія | Обрані технології | Обґрунтування вибору |
| :--- | :--- | :--- |
| **Мови програмування** | Python 3.11+, TypeScript, SQL | Python для backend-сервісів та обчислювального ядра. TypeScript для типобезпечного React клієнта. |
| **Архітектурні патерни** | Clean Architecture, SOA, Asynchronous Task Queue, Multi-Tenancy, Circuit Breaker | Забезпечення розширюваності, ізоляції доменного ядра, стійкості до відмов зовнішніх API та асинхронності задач. |
| **Backend & Solvers** | Django REST Framework, FastAPI, Google OR-Tools (CP-SAT), Celery | DRF для управління IAM та бізнес-сутностями, FastAPI для високої швидкодії солвера OR-Tools, Celery для асинхронних черг. |
| **Frontend** | React (Vite), TypeScript | Швидка збірка та висока чуйність інтерфейсу користувача. |
| **Бази даних & Сховища** | PostgreSQL (`pgvector`), Redis | PostgreSQL для реляційних даних та векторного пошуку HNSW. Redis як брокер повідомлень Celery та кеш. |
| **Зовнішні інтеграції** | Google Gemini API, Mapbox API, Google Places API | Gemini для NLP та генерації embeddings. Mapbox для матриці відстаней та геокодування. |
| **Observability & DevOps** | Docker, Prometheus, Grafana, OpenTelemetry | Контейнеризація та повний моніторинг обчислювальних ресурсів і метрик солвера. |

**### DevOps, інженерія якості та спостережуваність
- **Docker, Docker Compose:** Контейнеризація мікросервісів (`api-gateway`, `optimization-service`, `ai-orchestrator`, `notification-worker`, `pgvector`, `redis`) та оркестрація локального середовища розробки.
- **GitHub Actions:** Конвеєр безперервної інтеграції (CI) для автоматичного запуску лінтерів, тестів та сканування контейнерів при кожному push/PR.
- **pytest, coverage.py:** Автоматизоване unit- та integration-тестування REST API endpoints, доменної логіки солвера OR-Tools та асинхронних Celery-задач із контролем покриття коду.
- **Ruff, mypy:** Статичний аналіз коду, автоматичне форматування та сувора перевірка статичної типізації Python 3.11+.
- **Trivy:** Автоматичне сканування Docker-образів на наявність відомих вразливостей (CVE) у конвеєрі CI/CD.
- **Prometheus, Grafana:** Збір та візуалізація системних метрик (CPU/RAM) і специфічних метрик солвера (час розв'язання VRPTW, кількість обмежень, частка UNSAT-задач, глибина черги Celery).
- **OpenTelemetry:** Наскрізне розподілене трасування запитів між `api-gateway`, `ai-orchestrator` та `optimization-service`.
- **Alembic / Django Migrations:** Версіонування та безпечне застосування міграцій схеми PostgreSQL (включаючи векторні індекси `pgvector`).

- **Documentation as Code:** Зберігання всієї проєктної та технічної документації у форматі Markdown у Git-репозиторії поруч із вихідним кодом.

- **Architecture Decision Records (ADR):** Фіксація та версіонування критичних архітектурних рішень (вибір CP-SAT солвера, ізоляція орендарів, патерн асинхронних черг).
- **C4 Model (Structurizr / PlantUML):** Візуалізація архітектури системи на рівнях System Context, Container (взаємодія сервісів) та Component (внутрішня структура солвера та gateway).

## 7. Очікувані результати

1. **Працездатна хмароорієнтована платформа:** Повнофункціональна вебсистема з рольовим розмежуванням доступу (RBAC) та ізоляцією даних орендарів закладу (`Venue`) на рівні ORM-запитів.
2. **Універсальне математичне ядро комбінаторної оптимізації:** Сервіс на базі `Google OR-Tools (CP-SAT)`, що розв'язує дві споріднені задачи — побудову реалізовного маршруту подорожі (VRPTW) та розподіл ресурсів і графіку персоналу закладу.
3. **Асинхронний подієво-керований контур:** Надійна обробка важких обчислювальних задач через Celery/Redis із підтримкою статусного моніторингу (polling/SSE) та патерну Circuit Breaker для зовнішніх API (Mapbox, Gemini).
4. **Модуль семантичного пошуку та рекомендацій:** Інтегроване розширення `pgvector` для знаходження релевантних закладів на основі косинусної схожості векторних вкладень (embeddings).
5. **Автоматизований конвеєр CI/CD:** Налаштовані GitHub Actions зі статичним аналізом (Ruff/mypy), автоматичним тестуванням (pytest) та безпековим аудит-скануванням (Trivy).
6. **Контур спостережуваності (Observability):** Моніторинг метрик обчислювальних задач у Prometheus/Grafana та наскрізне трасування ланцюжків запитів через OpenTelemetry.
7. **Комплект технічної документації:** Специфікація OpenAPI, ADR-записи, C4-діаграми архітектури та пояснювальна записка з формалізацією математичної моделі VRPTW і результатами навантажувального тестування.**
