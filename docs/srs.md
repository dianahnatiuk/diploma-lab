## 1. System Context

### 1.1. Призначення та межі системи (Scope)

Система призначена для оформлення передзамовлень, ведення віртуальної черги, безконфліктного бронювання місць (столиків і коворкінг-місць) та нарахування бонусів у мережі кав'ярень. Серверна частина реалізується на Python 3.11+ (FastAPI, Celery), дані зберігаються в PostgreSQL, Redis застосовується для блокувань, розсилання подій і черги фонових задач. Клієнтські інтерфейси реалізуються на Flutter.

**У межах системи:** замовлення та оплата через платіжний шлюз, віртуальна черга, карта залу та бронювання, автозвільнення броней, бронювання під замовлення, коворкінг-сесії, програма лояльності з антифрод-правилами, рольовий доступ, панель менеджера, спостережуваність.

**Поза межами системи:** фіскалізація розрахункових операцій (РРО/ПРРО), інтеграція з POS-терміналами, обробка даних платіжних карток (виконується платіжним шлюзом), промислова експлуатація (розгортання виконується в демонстраційному середовищі на одному вузлі Docker Compose).

- Усі часові значення зберігаються та передаються в UTC (ISO 8601); перетворення в локальну часову зону виконує клієнт.

### 1.2. Актори та зовнішні системи

| Актор / система | Тип | Взаємодія із системою |
| :--- | :--- | :--- |
| Клієнт | Користувач | Формує замовлення, оплачує, бронює місце, користується коворкінгом, отримує бонуси |
| Бариста | Користувач (персонал) | Отримує нові замовлення, змінює статуси приготування |
| Адміністратор залу | Користувач (персонал) | Контролює бронювання, підтверджує прибуття клієнтів |
| Менеджер мережі | Користувач | Керує меню, цінами, акціями, конфігурацією залу |
| Платіжний шлюз | Зовнішня система | Приймає запити платежу, надсилає webhook про статус (тестовий режим sandbox) |
| Firebase Cloud Messaging (FCM) | Зовнішня система | Доставляє push-сповіщення на мобільні пристрої |

### 1.3. Зовнішні інтерфейси

| ID | Інтерфейс | Протокол | Напрям |
| :--- | :--- | :--- | :--- |
| EXT-01 | Клієнтський застосунок та консоль персоналу, команди та запити | REST / HTTPS (TLS 1.2+), специфікація OpenAPI 3.0 | Клієнт → система |
| EXT-02 | Події реального часу для клієнта та персоналу | WebSocket (RFC 6455) поверх TLS | Система → клієнт |
| EXT-03 | Створення платежу | REST / HTTPS | Система → платіжний шлюз |
| EXT-04 | Статус платежу | Webhook / HTTPS | Платіжний шлюз → система |

### 1.4. Обмеження та припущення

- Стек: Python 3.11+, FastAPI, Celery, PostgreSQL, Redis, Flutter, Docker Compose.
- Середовище виконання демонстраційне: один вузол, без кластеризації баз даних; реплікація PostgreSQL не передбачена, відновлення забезпечується резервним копіюванням.
- Платіжний шлюз використовується в тестовому режимі; реальні платіжні дані не обробляються.
- Автентифікація реалізується в самій системі (JWT, сумісний з OAuth 2.0); зовнішній Identity Provider не використовується.

| <a id="srs-nfr-rel-03"></a>SRS-NFR-REL-03 | Надійність | Автозвільнення бронювання повинно виконуватися з відхиленням не більше 60 с від налаштованого інтервалу. |

| <a id="srs-nfr-sec-02"></a>SRS-NFR-SEC-02 | Безпека | Контроль доступу повинен діяти за принципом deny by default для 4 ролей (RBAC); запит без права на ресурс повинен завершуватися кодом 403. |
| <a id="srs-nfr-sec-03"></a>SRS-NFR-SEC-03 | Безпека | Транспорт повинен використовувати TLS не нижче версії 1.2; сканування OWASP ZAP baseline повинно виявляти 0 знахідок рівня High. |
| <a id="srs-nfr-sec-04"></a>SRS-NFR-SEC-04 | Безпека | Образи контейнерів повинні мати 0 вразливостей рівня CRITICAL та 0 виправних вразливостей рівня HIGH. |
| <a id="srs-nfr-sec-05"></a>SRS-NFR-SEC-05 | Безпека | Система повинна обмежувати частоту запитів (Rate Limiting): не більше 100 запитів на хвилину на користувача та 20 запитів на хвилину з однієї IP-адреси для ендпоінтів автентифікації; перевищення повинно завершуватися кодом 429. |
| <a id="srs-nfr-sec-06"></a>SRS-NFR-SEC-06 | Персональні дані | Система повинна зберігати мінімально необхідні персональні дані, не повинна зберігати дані платіжних карток і повинна видаляти або знеособлювати дані користувача протягом 30 днів після запиту на видалення (GDPR). |
| <a id="srs-nfr-sec-07"></a>SRS-NFR-SEC-07 | Безпека | Система повинна вести журнал подій безпеки (входи, зміни ролей, скасування бронювань) із зберіганням не менше 90 днів. |
| <a id="srs-nfr-qual-01"></a>SRS-NFR-QUAL-01 | Якість коду | Покриття тестами модулів бронювання та лояльності повинно становити не менше 80 %; перевірки Ruff, mypy та Bandit повинні завершуватися без помилок. |
| <a id="srs-nfr-qual-02"></a>SRS-NFR-QUAL-02 | Інфраструктура | Усі сервіси повинні бути контейнеризовані; середовище повинно запускатися однією командою `docker compose up`; конвеєр CI повинен виконуватися не довше 10 хв. |
| <a id="srs-nfr-obs-01"></a>SRS-NFR-OBS-01 | Спостережуваність | Система повинна експортувати метрики Prometheus (затримка, частка конфліктів бронювання, глибина черги Celery, кількість WebSocket-з'єднань) та трейси OpenTelemetry, що охоплюють ланцюг API → Worker → PostgreSQL. |

## 5. Glossary

| Термін | Визначення |
| :--- | :--- |
| Race condition | Стан, за якого результат операції залежить від порядку виконання конкурентних запитів; у системі проявляється як подвійне бронювання одного місця |
| Distributed Lock | Розподілене блокування в Redis (команда SET з параметрами NX та PX), що забезпечує виключний доступ до ресурсу між екземплярами API на обмежений час |
| Exclusion constraint | Обмеження цілісності PostgreSQL (EXCLUDE USING gist), що забороняє перетин значень, зокрема інтервалів часу для одного місця |
| Idempotency Key | Унікальний ідентифікатор запиту, за яким сервер повертає збережений результат першого виконання замість повторного виконання операції |
| Redis Pub/Sub | Механізм публікації та підписки в Redis, що доставляє повідомлення активним підписникам без їх збереження |
| p95 Latency | Значення часу відповіді, не перевищене у 95 % запитів |
| Ledger | Журнал операцій, що допускає лише додавання записів; баланс бонусів визначається сукупністю записів |
